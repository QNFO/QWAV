## 0. The Reframe

strategy/2.0.md asked: "What should we do while we wait for applications to respond?"

The answer was: monitor. Wait. Don't initiate.

This is correct defensive strategy. It is also **strategically inert**. The program that built 5 publications, computational evidence at depth 7, 48× error reduction, a glass-box AI architecture, and 673 prior releases was not built by waiting. It was built by *building*.

**The reframe:** Stop asking "what do we do while we wait?" Start asking "what do we build that makes waiting irrelevant?"

**The principle:** Endogenous momentum > exogenous validation. Build something that creates its own gravitational pull. If the applications come back positive, the built assets amplify the outcome. If they come back negative, the built assets ARE the outcome -- a program too substantial to ignore.

**The constraint:** Everything must be completable by a solo founder with LLM augmentation, computational tools only, written-only distribution, no external dependencies, no live interaction, and no institutional backing.

**The question is not whether this is possible.** It already happened -- 5 publications, 7 sprints of computational validation, the Q-PNA architecture. The question is: what's the NEXT thing to build, at what cadence, to what cumulative effect?

## 1. The Gravity Principle

### 1.1 Why "Inbound-Only" Became "Nobody's Coming"

The inbound-only strategy was correct in principle: don't chase, attract. But it was missing the attraction mechanism. Publishing a paper and posting it to social media is not attraction -- it's distribution without gravity. The paper drifts past timelines and disappears.

**Gravity = something people come back to. Something they explore. Something they share because it's interesting in itself, not because they were asked to.**

Examples of gravity-generating assets:
- An interactive simulation where you can watch error suppression happen in real time
- A knowledge graph where you can explore how ultrametric geometry connects quantum computing, AI, spin glasses, protein folding, and cosmology
- A publication timeline showing intellectual evolution across 673 releases
- A "try it yourself" code environment with one-click execution
- A visual proof that the strong triangle inequality geometrically suppresses errors

None of these require a lab. None require peer review. None require live interaction. None require external collaborators. All are completable in single LLM threads. All honor D1-D13.

**The shift:** From "we published -- please read" to "we built something you'll want to explore." The inbound contact becomes a natural consequence of the asset, not a hoped-for response to a paper.

### 1.2 The Gravity Flywheel

```
BUILD interactive artifact (30-second demo)
        ↓
PUBLISH with DOI (permanence)
        ↓
DISTRIBUTE artifact link via social (not paper link)
        ↓
VISITOR explores artifact, stays, clicks to related content
        ↓
VISITOR finds the paper (on their own, because they're interested)
        ↓
VISITOR reaches out OR shares OR cites
        ↓
EACH new artifact adds to the gravity well -- cross-links, cumulative depth
        ↓
OVER TIME: the program becomes a destination, not a sender
```

The flywheel spins on its own once it has enough mass. The current program has 5 papers and 2 GitHub repos -- not enough mass to spin the flywheel. The strategy is to add mass systematically until it spins.

## 5. What This Strategy Does Differently

### 5.1 From Passive to Active

| Dimension | Strategy 2.0 | Strategy 3.0 |
|:----------|:-------------|:-------------|
| **Posture** | Monitoring. Waiting. | Building. Publishing. Growing. |
| **Primary activity** | Check inbox. Check application status. | Build interactive artifacts. Publish regularly. Grow the evidence stack. |
| **Success metric** | Inbound contact. Application acceptance. | Cumulative gravity: number of artifacts, site visitors, time-on-page, return visits, inbound contacts (as natural consequence). |
| **Application role** | The main event -- everything waits on outcomes. | Background process -- the program builds regardless. |
| **Temporal orientation** | "When X happens, we'll..." | "Every week, we build Y. X might happen -- if it does, it amplifies Y." |
| **External perception** | 5 papers, silence. | Living ecosystem. Regular updates. Visible momentum. |

### 5.2 What Stays the Same

All 13 constraints (D1-D13) remain non-negotiable. All deprecated activities (§7 of 2.0) remain deprecated. The venue architecture (§4), vision layers (§3), and corpus strategy (§5) from 2.0 are unchanged. This strategy changes the forward work plan and posture -- not the identity or constraints.

### 5.3 The Honest Acknowledgment

This strategy requires the founder to *build in public* -- to deploy interactive artifacts, maintain a public site, publish regularly, and sustain a visible cadence. This is more work than the monitoring posture of 2.0.

**The trade-off:** More output. More visibility. More gravitational pull. Also more effort, more sessions, more sustained attention.

**The bet:** The effort of building gravity is less than the cost of waiting -- which is demoralization, stagnation, and the slow erosion of belief that the work matters.

**The backup:** If the 30-day build phase produces zero detectable engagement (no site visitors, no artifact interactions, no inbound contacts), the program has learned something valuable: the problem is not substance or presentation -- it's discovery. At that point, the strategy pivots to distribution and bridge content, not more artifacts.

## 7. Decision Required

This strategy requires founder approval on one key question:

**Do we shift from "monitor and wait" to "build and grow"?**

The 30-day build plan is concrete, constrained (D1-D13 compliant), and reversible. If it fails, the program returns to monitoring posture with more assets than it started with. If it succeeds, the program has gravitational pull that makes application outcomes secondary.

**The alternative:** Continue the monitoring posture of strategy/2.0. Wait for application responses. Do not initiate new activity. Accept that the program is externally-paced rather than internally-driven.

**Recommendation:** Build. The worst case is that we spend 30 days creating interactive artifacts that nobody visits -- which is the same outcome as spending 30 days waiting, but with assets deployed and lessons learned. The best case is that we create a program with its own gravity.

### 9.2 Interactive Artifact Deployment Recipe

Each artifact (A1-A5) follows this standardized deployment:

```
1. Create Pages project: wrangler pages project create <artifact-name>
2. Deploy from local dir:  wrangler pages deploy <dir> --project-name <name> --branch main
3. Set custom domain:      wrangler pages project set-domain <name> <domain>.qnfo.org
4. Verify:                 curl -sI https://<domain>.qnfo.org → 200
5. Cross-link:             Update all other artifact READMEs with new artifact link
```

**Time:** 15 minutes per artifact. **Cost:** $0. **Repeatable:** Yes — the `CLOUDFLARE-DEPLOYMENT` template automates this.
