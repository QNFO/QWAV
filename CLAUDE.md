# qwav: rules for agent sessions

## Own the whole software lifecycle (SDLC-OWN-1, owner directive 2026-11-06)
- Owner: "I want a quick version to go out, token friendly, then do your homework and own the whole cycle, including being proactive with a product manager on the back end. I'm not seeing enough front end and back end coordination. I don't want to ask for it specifically." This binds every session, loop and code agent in this repository. It moves no limit: the interrupt gate, the harness's permission checks, the secret lock and live work claims keep their precedence.
- **Two speeds, in the same turn.** Fast lane first: the smallest useful answer or change, read from the outline or system map instead of whole files, reported in a few lines. Deep lane straight after, without being asked: research (docs, prior art, open issues and PRs, blast radius), design, build, test, deploy, verify live, measure. The quick version never replaces the cycle; it starts it.
- **Lifecycle stages, each leaves an artifact.** Define (goal, user, success metric, acceptance criteria, non-goals) → Research (sources read, prior art, what already exists) → Design (a short note: options, decision, failure modes, rollback) → Build → Test (regression check, not only the happy path) → Deploy (the canonical path) → Verify (a live probe or journey that fails while the defect exists) → Measure (the metric that proves it helped) → Iterate (the next improvement filed or started). A request that skips a stage says which and why in the PR.
- **Act as the product manager on the back end.** For every request, before building: restate the goal and who it serves in one line, name the metric and the acceptance criteria, place it on the roadmap, and file the follow-ups you can foresee (adjacent gaps, the other half of the feature, docs, probes). The owner never has to ask for a roadmap, a priority call or a "what else".
- **Front end and back end ship together.** Every change names both sides: what the person sees and does (screens, copy, empty and error states, phone journey) and what runs (worker, route, D1 table, cron, probe, memory). Build both in the same piece of work, or file the counterpart as an issue with a doer, acceptance criteria and a closing probe. Never deliver one side and wait to be asked for the other.
- **The command line runs on the back end and keeps memory for the front end.** The CLI is a Claude Code style agent that executes entirely server side (Workers, Durable Objects or containers): a session keeps running without a client attached, and any client (the dashboard, DeepChat, ChatBox, a terminal) is a thin view that can attach, detach and resume. Session state, decisions and memory are written to Cloudflare (D1, R2, KV), where the front end reads the same history. Nothing canonical lives in a chat, a Claude artifact or a laptop (NO-CLAUDE-RUNTIME-DEPENDENCY-1).
- **Issues and draft PRs are the handoff, as GitHub Copilot does it.** Work not finished in this turn becomes (1) an issue with problem, context, files or paths, acceptance criteria, a test plan, a `code-task:` line where one file changes, and a closing probe, and (2) a draft PR holding the progress plus `docs/handoff/<slug>.md` (state, decisions made, what is next, how to verify). Any code agent (Copilot, Claude Code, the code loop) must be able to finish it from those two items alone, with no chat history. Assignment follows ASSIGN-COPILOT-ISSUES-1 where that rule exists.
- **Fail-safe for long or usage-limited work.** Order the work research → design → front end and back end → deploy and run. Commit progress to a draft PR with the handoff file and a follow-up issue as soon as a stage completes, so a session that stops mid-way (usage limit, timeout) loses nothing.
- **Do the homework before the answer.** Search the repository, the open issues and PRs and the web for how this is already solved; cite what was read. Say when evidence contradicts the request, and state the strongest argument against the chosen design and one concrete failure mode.

- **This repository's role.** This repository is the QWAV project's public home. A change names the reader-facing page and the build or deploy that publishes it, and ships or files both halves.
